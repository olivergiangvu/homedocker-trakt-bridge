## Still OPEN / blocking a production release

1. **Automated boot-time fence:** B1Q validated a transient systemd one-shot; B1R now tests an **installed, enabled, continuously supervised systemd unit** on disposable GitHub runner. It automatically disconnects a fake gateway on missing nft, re-attests/readmits on repair and binds to Docker service lifecycle. **B1S separately qualified guest boot-ID-changing QEMU kernel reboot and guest systemd/Docker cold-start HOLD. Still OPEN:** production-shaped Gateway/container admission across that reboot, privileged Docker API launch bypass (explicitly reproduced in B1S), external operator/app interference, and independent immediate deny during monitoring process/supervisor failure. A QEMU guest reboot smoke is not full production Gateway cold-boot qualification.
2. **Independent fail-closed guardian/kill path:** B1O verified reciprocal process SIGKILL stops the fake server, while simultaneous death originally left authorized TCP reachable. B1P **closed that specific dual-death case in a disposable lab** with a 3-second kernel-expiring nft lease; live server stays up but new/established TCP stops when the kernel timeout expires. **Still OPEN:** an independently enforced default-deny boot controller that remains safe on total nft policy loss, veth/bridge recreation, host reboot, unexpected process starts, and authorized production clients. The 3-second delay is not instantaneous.
3. **Independent fence after actual Docker/network policy loss:** B1M qualified total nft loss only inside a disposable namespace with unchanged veth. B1N confirmed new Docker veth loses old tc. B1Q demonstrated deleting sole nft lease while fake server attached makes authorized TCP reachable; exact Docker network detach cuts it. **B1R demonstrated automated, bounded-polling monitor-triggered detach after nft-table loss**, not a zero-gap kernel block. **Still OPEN:** a real `total nft ruleset flush` under production-shaped Docker while traffic is attached, and an independently enforced atomic/hard deny at the instant total nft policy disappears, including monitor+systemd failure, unexpected privileged container starts, veth/bridge recreation, true reboot and non-internal production NAT.
4. **Production-shaped Docker integration:** B1N qualified **internal** Docker/veth/daemon recovery; B1T now qualifies a **non-internal** Docker bridge with actual egress SNAT to an isolated fake external namespace, a real loopback-only published TCP port, forbidden unbound host port, exact disconnect-to-cut, and denied Docker socket access for ordinary UID 65534 without supplemental groups. **Still OPEN:** combine independent tc+nft admission with NON-INTERNAL published-port INPUT/FORWARD and DNAT/conntrack behavior, remote host/LAN probe, IPv6 and full policy loss/restart/reboot. Do not treat root or Docker-group privilege as controlled; B1S proved privileged API admission bypass.
5. **Unified Gateway functional acceptance:** B1U now adds an executable two-account **synthetic** AIO/Jellyfin HTTP contract: NextUp only normalizes verified aliases for the configured same user, stale/missing graph leaves source intact, Resume modern+legacy bytes/pagination remain AIO-owned, no mutating playback/history route or second writer exists in the exercised Gateway paths. **B1V adds only an opt-in, locally run READ-ONLY AIO→Gateway comparator with existing hidden session token, fixed localhost GET targets, strict item/Resume preservation and pre/post snapshot race checks; its synthetic 13-test CI passing is NOT live host evidence. Still OPEN:** production-authenticated cross-user Resume ACL (the B1U 403 was simulated by the mock upstream), real Jellyfin/Remux/Trellis/Strand client resumes, Trakt canonical history convergence/scrobble and write ownership across running services. Preserve single Bridge and no duplicate history writer.
6. **Release engineering:** build a coherent `1.4.0-rc` candidate after blockers, qualification/soak, SQLite online backup and one-service rollback rehearsal. Only after observed host protection and exact digest checks can `v1.4.0` stable tag be approved.

**Dangerous false shortcut:** passing GitHub CI on an isolated namespace does not prove HomeDocker boot/daemon restart safety. Tagging `v1.4.0` would trigger the repository's release workflow, publish a stable GHCR image and potentially move `:latest`. A CI fail-fast gate has therefore been added to the release workflow for `v1.4*` tags until a separate reviewed change explicitly lifts it after complete qualification. This gate is a workflow safeguard **only for tagged commits containing the updated workflow**; GitHub tag protections or rulesets are still recommended to prevent creating tags from older unguarded commits.
