# v1.2.0-rc.1 — Native Trakt coexistence hardening

Status: **release candidate / HomeDocker canary only**.

`v1.1.0` remains the stable production release until this candidate passes the acceptance gate below.

## Why this candidate exists

Issue #58 was opened after production evidence showed a stale-resume race under shared Trakt rate pressure:

1. AIOStreams queued playback transitions while Trakt returned `429` with multi-minute `Retry-After`.
2. Playback continued and a newer position was observed.
3. A newer pause could fail while the account was still rate limited.
4. Older queued AIOStreams retries could later succeed and rewrite Trakt resume state backwards.

The HomeDocker requirement is to keep native Trakt enabled on capable clients such as VidHub and Strand. The bridge must therefore coexist with other authenticated Trakt writers rather than assume exclusive ownership of the user's write budget.

## What changes

### Stale playback protection

For `start`, `pause`, and `stop`, the bridge persists the newest AIOStreams event timestamp seen for the resolved canonical Trakt movie/episode.

An older retry is ACKed and ignored with:

```text
ignored=stale_playback_event
```

The watermark is advanced before the upstream Trakt call. This prevents an older retry from overtaking a newer playback event even when the newer event itself receives `429` or `422`.

Ordering is based on event time, not progress. A newer seek backwards therefore remains valid.

### Better 422/429 diagnostics

The bridge now retains only safe, bounded upstream metadata:

- HTTP status;
- endpoint;
- `Retry-After`;
- parsed `X-Ratelimit` name/period/limit/remaining/until;
- short upstream error/message text.

Authorization headers, OAuth tokens and arbitrary full response bodies are never persisted.

### Rate-limit lane isolation

Cooldown handling is now split into:

- read;
- write;
- shared/security.

A confirmed `AUTHED_API_POST_LIMIT` response pauses bridge writes without unnecessarily blocking GET-based pull convergence.

A confirmed `AUTHED_API_GET_LIMIT` response pauses reads.

Unknown or headerless `429` responses remain conservative shared cooldowns and block both lanes.

## What does not change

- v1.1 semantic history dedupe remains unchanged.
- `HISTORY_DEDUPE_SECONDS=300` remains the recommended HomeDocker setting.
- `PULL_IDENTITY_MODE=trakt` remains the recommended native-Trakt coexistence mode.
- Pull cache representation and namespace remain unchanged.
- DB schema remains `1`; there is no migration.
- Native Trakt should remain enabled on supported clients during canary testing.

## Intentionally deferred from rc.1

### Pause 422 recovery

Production evidence showed a `/scrobble/pause` 422 after earlier rate-limited playback transitions. The current hypothesis is that Trakt had no compatible active scrobble state, but v1.1 did not preserve the upstream error body.

rc.1 captures the sanitized upstream reason first. A bounded recovery such as `start -> pause` will only be added if the real response confirms that behavior.

### Partial-playback unplayed reduction

Some Jellyfin-compatible flows emit `unplayed` after partial playback transitions. rc.1 does not suppress those writes because an explicit mark-unplayed operation must remain correct. This remains an observation item for later v1.2 work.

## HomeDocker canary configuration

Keep the accepted production settings:

```env
PULL_IDENTITY_MODE=trakt
PULL_CACHE_TTL_SECONDS=60
PULL_HINT_SECONDS=60
HISTORY_DEDUPE_SECONDS=300
```

Use the exact rc.1 image digest published by the release workflow. Do not deploy the mutable tag.

## Acceptance gate

With native Trakt still enabled on VidHub and Strand:

- `/health` reports `1.2.0-rc.1`;
- `/readiness` remains ready with DB schema `1` and the existing connected profile;
- a stale retry after a newer playback event is logged as `stale_playback_event` and does not call Trakt;
- a legitimate newer backwards seek still reaches Trakt;
- a confirmed POST-only rate limit does not unnecessarily block pull GETs;
- headerless/security-style 429 remains shared/conservative;
- 422 diagnostics include a bounded upstream reason when Trakt provides one;
- no regression appears in v1.1 semantic history dedupe, legitimate rewatches, watchlist, OAuth or identity behavior;
- container remains healthy with no restart loop.

The canary is successful even if native clients still consume the shared Trakt user-level write budget; rc.1 is expected to protect Bridge correctness and convergence, not to control writes made by other applications.
