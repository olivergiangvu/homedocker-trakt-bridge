# HomeDocker Trakt Bridge v1.4.0 Stable — RC7 completion and release gates

**Status (2026-10-15): DEVELOPMENT / NOT RELEASED.** This document defines the v1.4.0 **target**; it is not a released build, a running host image, or authorization to merge/deploy. Keep `v1.3.0` published tag and production RC6 immutable, with the current AIOStreams `latest` container and native host nginx untouched until opt-in release approval.

## Product architecture: ONE Trakt Bridge product and dashboard

The **AIO Identity Gateway is an internal Trakt Bridge v1.4.0 module**. It uses the existing Bridge profile-scoped verified identity registry, existing profile/admin authorization and **existing UI/dashboard**. It must not become a separately administered service, duplicate dashboard, Trakt connector, identity database, or watch-state store. A separate runtime listener/process is allowed only for network isolation and remains managed by Bridge.

**Active use case:** AIOStreams owns watch state for trackerless shell clients (Odin / AIOStreams Desktop). Trakt native engines remain authoritative for their own clients. Strand uses native Trakt; Trellis is a Strand-compatible passthrough; Remux is fallback/backup; CrossWatch is secondary/inactive for this flow. Do not alter their pipelines for this release.

**Identity behavior:** Trakt Bridge holds validated alias evidence; the optional Jellyfin NextUp response filter changes only read-only representation after same-user authentication and verified `SeriesId -> show IMDb` metadata resolution. It does **not** merge AIO's two underlying watch-state families. Resume has passed exact upstream passthrough parity, but **Resume normalization is NOT implemented or release-approved**. No auto-drop, fabricated IDs, history rewrite, AIO source/image fork, pin or direct SQLite write.

## Dashboard v1.4 contract

One Bridge dashboard must show:
- Whether the gateway is disabled, configured but not listening, or listener active **without falsely claiming client routing or effective identity normalization**.
- Matched exact Bridge Trakt profile, verified identity show/alias aggregate, registry revision and conflict counts **without exposing profile IDs, raw auth tokens, Jellyfin user IDs, credentials or original cache records**.
- NextUp normalization decision counters, fail-open reasons, last upstream success/failure and latency in a later monitored phase; no plaintext watched-history logging.
- A read-only diagnostic/preview and explicit disable/rollback controls **only after implementation, validation and operator approval**. Until then all routing and config remain manual/default-off.
- Resume `off` versus `raw_passthrough`; no misleading `normalized` state.

**Current code milestone:** `src/gateway-dashboard.mjs`, `GET /u/{profileId}/gateway/status.json?key=<existing setup key>`, existing /setup admin and /u/profile/setup panels. The Bridge's existing setup key guards the new endpoint; no new login. It calls `db.cachePeek()` to avoid `cacheGet()`'s expiry/corruption cleanup mutation. All diagnostics are aggregate only; UI reports `productionRoutingQualified=false` until genuine evidence is wired in. Gateway remains disabled by default.

3. **Safe response:** one card only when uniquely verified and non-competing; ambiguity, unknown user, missing metadata, third duplicate, pagination uncertainty, errors => **fail open** with unmodified response; no hidden active resume.
4. **Client reachability:** prove Odin/AIO Desktop use the selected Jellyfin API routes; if clients use native non-Jellyfin AIO APIs, document gateway coverage as limited instead of claiming convergence.
5. **Ingress:** exact-route proxy only; never blanket `/jellyfin` to the gateway. Keep auth, catalog, playback, stream, WebSocket and any unrecognized routes directly to AIO. Validate on HTTPS/nonstandard-port ingress and a **single canary client** before any shared-host cutover.

7. **Operations:** test restarted Bridge and AIO latest, service failure/timeouts, pinned rollback, rate limits, CPU/RAM; ensure Trakt history/scrobble flows remain unchanged; check restore to new host preserves the configured mapping.
8. **Release:** all required CI/tests green, production pilot reviewed, clear operator authorization, documented rollback, then version bump/tag/deploy. Otherwise keep feature branch DRAFT and RC6 production untouched.

## v1.4 Gateway telemetry (development-only)

The gateway listener now exports a **process-internal**, in-memory `gatewayMetricsSnapshot()` accessor to its owning Trakt Bridge server. This is **not** a gateway HTTP route; it is available only to the authenticated Bridge dashboard and status API. Counts cover the **whole listener** (not individual user or Trakt profile), reset on Bridge restart, and are shown only to the explicitly mapped profile. It reports request counts, responses where NextUp filtered cards, removed-card totals, unchanged replies, caught normalization exceptions (fail-open errors), upstream HTTP non-200, transport failures, response failures, and oversized/invalid JSON passthrough outcomes. No raw request path, user ID, token, IP, episode ID, show ID, watched position or timestamps are captured.

**Interpretation:** `nextUpNormalizedResponses=0` does not imply no alias identity problem: live NextUp may not include a verified alias pair, or client may bypass the gateway. `failOpenNormalizationErrors` only counts caught exceptions; ambiguous but intentionally unchanged responses are counted as unchanged, not errors. Listener-wide counts do not establish which client or account generated traffic. Production routing remains disabled until independently qualified.

## v1.4 gateway traffic-load protection (development only)

The Gateway now bounds metadata request concurrency **across the entire integrated listener** to six active upstream `/Items/{SeriesId}` lookups, with at most 96 waiting tasks; a full queue throws inside normalization and causes fail-open original NextUp JSON.
