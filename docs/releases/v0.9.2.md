# v0.9.2 — Rate-limit-aware freshness hardening

Status: **published public pre-1.0 release / accepted HomeDocker production candidate**.

## Why this release exists

HomeDocker production telemetry on 2026-10-02 showed Trakt `429` responses on both playback writes and state pulls while testing lower freshness TTLs.

The clearest same-window sample was:

- `00:10:31` `/scrobble/start` → `429`, `Retry-After: 246`
- `00:13:16` `/sync/playback/movies?...` → `429`, `Retry-After: 81`

Both Retry-After values expire at approximately `00:14:37`, so the bridge treats an upstream `429` as a profile-wide cooldown rather than independent read/write buckets.

## Changes

- Serializes authenticated Trakt writes per profile with a 1.1 second minimum cadence.
- Any Trakt `429` arms one shared profile cooldown for both reads and writes.
- While a long Retry-After is active, writes fail fast with `429` + remaining Retry-After instead of keeping AIOStreams' HTTP delivery request open beyond its timeout.
- Pulls are blocked locally during the same cooldown, allowing Bridge stale-cache recovery to answer without touching Trakt again.
- Cooldown state is persisted through the existing `media_cache` table (`rate-limit:v1:<profile>`) and survives Bridge recreation/restart without a DB schema change.
- Observed Trakt `X-Ratelimit` metadata is retained for diagnostics; a reported zero remaining budget with an upstream reset time proactively arms the cooldown.
- Operator summaries retain upstream endpoint and Retry-After information.
- The release image is built and published through GitHub Actions with SBOM and provenance metadata.

## Safety

- DB schema remains `1`.
- AIOStreams watch-state representation and identity model are unchanged.
- `PULL_IDENTITY_MODE=trakt` remains required for the HomeDocker native-Trakt + AIOStreams coexistence model.
- Existing pull stale-cache behavior remains fail-safe: authoritative watched/watchlist sets are never reconstructed from a partial upstream answer.
- No AIOStreams Watch State environment overrides are required for the v1.0 baseline; HomeDocker keeps upstream AIOStreams runtime defaults while current end-to-end freshness remains satisfactory.

## HomeDocker source-canary acceptance

The source canary passed with:

- `/health` and `/readiness` healthy on v0.9.2 with DB schema `1`
- connected Trakt profile preserved across recreation
- runtime image approximately `120.25 MiB`
- settled memory approximately `18–21 MiB`
- dual-IMDb regression clean with Trakt identity authority preserved
- normal playback start/pause/stop writes succeeding without a new upstream `429`
- Bridge freshness accepted at `300s`, then `120s`, then `60s`, with zero upstream `429` and zero local cooldown during each acceptance window

Final freshness policy:

```text
Public default          PULL_CACHE_TTL_SECONDS=300
                        PULL_HINT_SECONDS=300

HomeDocker optimized    PULL_CACHE_TTL_SECONDS=60
                        PULL_HINT_SECONDS=60
```

The public default remains intentionally conservative. Lower Bridge TTLs should be treated as measured tuning, not universal copy-paste defaults.

## Rollback-gate note

A pre-v1.0 rollback rehearsal attempted to pull the historical `v0.5.0` GHCR tag. The test stopped before any production mutation because the registry currently returns `manifest unknown` for that container tag.

The Git tag and GitHub Release still exist, but the corresponding container manifest is not presently available. The historical tag will not be mutated or republished just to manufacture a rollback target.

The meaningful final rollback acceptance is therefore deferred to the v1.0 canary:

```text
v1.0.0 exact published digest
  -> accepted v0.9.2 exact published digest
  -> v1.0.0 exact published digest
```

This tests the rollback path users will actually need after v1.0 while preserving release immutability.

## Known non-blocking observation

Some HomeDocker Trakt history entries can appear twice for one viewing. Playback, resume, watched-state and identity behavior remain acceptable, so this is not a v1.0 blocker. Post-v1.0 investigation is tracked separately and should first isolate overlapping writers before adding Bridge-side heuristics.

The accepted exact v0.9.2 digest completed a 45.78-hour HomeDocker burn-in and is the qualified rollback baseline for v1.0.0.

Final audit highlights:

- health/readiness and OAuth/profile state remained healthy

- duplicate identity / duplicate Continue Watching remained absent through burn-in
