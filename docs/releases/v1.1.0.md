# v1.1.0 — Semantic Trakt history dedupe

Status: **stable**.

`v1.1.0` promotes the accepted `v1.1.0-rc.1` HomeDocker canary to the stable release line.

## What this release fixes

Issue #40 identified duplicate Trakt history writes that could survive event-ID idempotency because different AIOStreams event IDs represented the same final watched state.

The stable guard now:

- keys semantic dedupe by the resolved canonical Trakt movie/episode ID;
- suppresses repeated single-item `played` or `unplayed` writes inside `HISTORY_DEDUPE_SECONDS` (default `300`);
- remembers a completed `/scrobble/stop` only when Trakt returns `action=scrobble`, so a following explicit `played` cannot add the same viewing again;
- persists markers in the existing SQLite cache so a Bridge restart does not reopen the duplicate window.

## Safety boundaries

The guard intentionally does **not** collapse:

- `played -> unplayed -> played`;
- another movie or episode;
- a same-state event outside the configured window;
- a stop that Trakt reports as `action=pause`.

No DB schema migration, pull-state representation change, identity-mode change or pull-cache namespace change is required.

## HomeDocker canary evidence

The exact `v1.1.0-rc.1` image was run on the HomeDocker production stack before promotion.

Observed acceptance evidence:

- a repeated `unplayed` for the same canonical episode arrived with a different event ID 118 seconds later and was ignored as `recent_history_equivalent`;
- a normal `played` produced one `history:add`;
- a real rewatch roughly 34 minutes later, outside the 300-second guard window, produced another valid `history:add`;
- Trakt history increased by exactly one play for that legitimate rewatch;
- runtime remained ready with DB schema `1`, one connected profile, zero container restarts and no canary errors.

The HomeDocker client path used during qualification emitted explicit `played` events without a completion `stop`, so the completed-scrobble → explicit-played overlap remains covered by the release regression suite rather than by that live client trace.

## Recommended HomeDocker configuration

```env
PULL_IDENTITY_MODE=trakt
HISTORY_DEDUPE_SECONDS=300
```

HomeDocker may continue its measured freshness tuning:

```env
PULL_CACHE_TTL_SECONDS=60
PULL_HINT_SECONDS=60
```

## Upgrade

Run the stable release by immutable image digest after the release workflow publishes and smoke-tests it.

Do not use a mutable `latest` tag for HomeDocker production.

## Rollback

`v1.0.0` remains the deterministic rollback line. Because DB schema remains `1`, code rollback does not require a database migration or restore, although normal pre-upgrade backups remain recommended.
