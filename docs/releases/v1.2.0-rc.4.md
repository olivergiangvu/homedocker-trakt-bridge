# v1.2.0-rc.4 — write-family rate-limit isolation canary

Status: **release candidate / HomeDocker canary only**.

Stable remains `v1.1.0`. rc.3 remains the current host rollback/canary reference until rc.4 passes qualification.

## Why rc.4 exists

rc.3 successfully removed public metadata resolution from the playback hot path, but the HomeDocker VidHub canary exposed a second bottleneck:

```text
AIO redundant unplayed
  -> /sync/history/remove
  -> headerless Trakt 429 + Retry-After
  -> rc.3 LOCAL_WRITE_COOLDOWN
  -> pause/start/stop scrobbles blocked locally
```

The tested item retained the correct AIOStreams local state at 512411 ms / 2580000 ms (19.86%), while the real stop could not reach Trakt because an unrelated history-remove retry had cooled every authenticated write.

## What changes

### Family-specific ambiguous write cooldowns

Headerless/unnamed 429s now cool only the family that actually failed:

```text
GET                  -> read
/scrobble/*          -> scrobble
/sync/history*       -> history
/sync/watchlist*     -> watchlist
other writes         -> all-write
```

The authenticated write queue and 1100 ms pacing remain global, so writes are still serialized conservatively.

### Explicit Trakt buckets still win

If Trakt identifies `AUTHED_API_POST_LIMIT`, all authenticated write families cool together.

If Trakt identifies `AUTHED_API_GET_LIMIT`, the read lane cools.

Unknown named/shared limits remain conservative shared cooldowns.

### Persisted cooldown state

The rate-limit cache namespace advances to `rate-limit:v3:*`.

A still-live v2 `writeUntil` value is migrated conservatively as one all-write legacy window. New observations then use the v3 family-specific representation.

## What does not change

- direct provider-ID playback/history/watchlist transport
- source and canonical playback watermarks
- semantic history dedupe
- AIOStreams 90% watched threshold protection
- `PULL_IDENTITY_MODE=trakt`
- DB schema 1
- pull cache representation and namespace
- AIOStreams `WATCH_STATE_*` settings
- native Trakt on supported clients

## Why rc.4 does not suppress the redundant unplayed event

The captured AIOStreams event was `unplayed`, `played=false`, position 0 for `tt36885662:1:3`.

AIOStreams can emit the same semantic shape from both its generic UserData update route and explicit PlayedItems-delete/unmark routes. The Bridge therefore cannot safely infer user intent from this payload alone.

rc.4 preserves Explicit Mark Unplayed and fixes the availability failure at the rate-limit layer instead of adding an unsafe heuristic.

## Regression coverage

New tests prove:

1. headerless history 429 does not block scrobble;
2. headerless scrobble 429 does not block history;
3. explicit authenticated POST-bucket 429 still blocks every write family;
4. family-specific cooldown survives client reconstruction;
5. existing read/write isolation and global write pacing remain intact.

## HomeDocker canary acceptance

Keep native Trakt enabled.

Required checks:

1. exact rc.4 digest, health/readiness good, schema 1, zero unexpected restarts;
2. HomeDocker sink active; Odin retired;
3. trigger or reproduce a history-remove 429;
4. while the history lane is cooling, a newer partial playback stop must still reach `/scrobble/stop` or `/scrobble/pause`;
5. no public resolver requests appear in the playback hot path;
6. stale retry protection still rejects an older transition after a newer stop;
7. VidHub -> Strand resume is tested only after transport acceptance;
8. explicit Mark Unplayed remains functional after its own history lane is available.
