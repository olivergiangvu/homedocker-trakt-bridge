# v1.3.0-rc.4

This canary extends the v1.3 HomeDocker protections from a narrow false-`unplayed` guard into a history-lineage guard that also prevents stale `played` echoes from creating fresh Trakt history.

## What changed

- Adds opt-in `AIO_HISTORY_ECHO_GUARD=true`.
- Keeps single Mark Watched and Mark Unwatched available.
- Keeps native AIOStreams season/show bulk marks available.
- Journals exact AIO single-mark deliveries and their contemporaneous local state through the existing Bridge cache.
- Suppresses reproduced positive-resume and zero-position composite false-`unplayed` events using immutable event-time evidence.
- Keeps RC3 current-state proof as a conservative fallback.
- Persists the latest authoritative Trakt watched snapshot returned on Bridge pull.
- Suppresses a same-state single `played` echo when the fresh canonical snapshot already says the item is watched, preventing a new `watched_at=now` history entry.
- Suppresses a same-state single `unplayed` when the fresh canonical snapshot already says the item is unwatched.
- Suppresses single-mark sync fanout when at least 3 distinct items with the same mark kind are queued inside a 10-second AIO delivery cohort.
- Does not add a database schema migration and does not write the AIOStreams database.

## Why RC4 is needed

The 48-hour RC3 soak showed two independent correctness failures:

1. false `unplayed` events could remove valid Trakt history;
2. false `played` events could add a new Trakt play with a fresh timestamp, making old shows appear above genuinely recent viewing.

AIOStreams 2.35.9 stamps a single history mark with the current event time. Bridge historically mapped that event time directly to Trakt `watched_at`. When an old already-watched item was replayed as a state echo, Trakt therefore received a new play dated today.

## HomeDocker soak evidence

Corrected actual-soak history writes:

- `history:remove`: 87
- `history:add`: 38

The AIO `played` deliveries include four clear fanout cohorts:

- 3 items around 00:24:39
- 3 items around 02:16:41
- 14 items around 02:17:40
- 9 items around 08:07:49

Those cohorts account for 29/38 successful `history:add` writes, or about 76%.

One three-item cohort spans approximately 5.7 seconds, so the default RC4 cohort window is 10 seconds rather than 5. The larger cohorts include mixed shows and non-sequential episodes, which strongly indicates state synchronization rather than deliberate one-by-one marking.

## Guard policy

For single movie/episode marks:

| Incoming event | Fresh canonical Trakt state | RC4 |
|---|---|---|
| `played` | already watched | suppress same-state echo |
| `played` | unwatched | allow Mark Watched |
| `unplayed` | already unwatched | suppress redundant same-state mark |
| `unplayed` | watched | allow unless event-time evidence or cohort proves sync echo |

A genuine rewatch remains valid because it is carried by `start/pause/stop` and Trakt scrobble completion. The redundant `played` mark after completion is not needed to create the play.

## Canary configuration

```env
AIO_RECONCILER_MODE=compare
AIO_UNPLAYED_ECHO_GUARD=true
AIO_HISTORY_ECHO_GUARD=true

AIO_HISTORY_EVIDENCE_INTERVAL_MS=1000
AIO_HISTORY_EVIDENCE_LOOKBACK_SECONDS=120
AIO_HISTORY_EVIDENCE_MAX_ROWS=500

AIO_HISTORY_COHORT_WINDOW_MS=10000
AIO_HISTORY_COHORT_MIN_ITEMS=3
CANONICAL_HISTORY_MAX_AGE_SECONDS=900
```

Public default remains:

```env
AIO_HISTORY_ECHO_GUARD=false
```

## Residual trade-off

A client that implements a genuine user action as 3 or more separate single-item marks within 10 seconds, instead of AIO's native bulk event, can look like sync fanout and be suppressed. Normal isolated manual marks and native season/show bulk marks remain supported.

RC4 must complete controlled qualification and a corrected natural-use soak before stable promotion.
