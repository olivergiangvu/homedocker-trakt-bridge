# v1.2.0-rc.3 — Odin-hybrid lean transport canary

Status: **release candidate / HomeDocker canary only**.

Production remains on the accepted `v1.2.0-rc.2` digest until this candidate passes host qualification.

## Why rc.3 exists

The rc.1/rc.2 VidHub canaries showed that HomeDocker Bridge could perform public Trakt metadata lookups before every useful playback write. Those lookups created real `429` failures on resolver endpoints and could delay the authenticated scrobble that AIOStreams needed for cross-client resume.

A controlled comparison with the original Odin Trakt Bridge showed a simpler pattern:

```text
AIO event
  -> provider IDs + season/episode
  -> one authenticated Trakt write
  -> invalidate pull cache
```

Odin avoided the resolver-429 path and, in one control run, preserved VidHub -> Strand resume at 544787 ms -> 544786 ms even though AIOStreams still emitted redundant `unplayed` noise.

Odin is not used as a complete correctness baseline. Repeated tests still showed intermittent Strand -> VidHub drift and duplicate visible Trakt history.

## What changes

### Direct provider-ID transport

Normal playback, history, bulk-history and watchlist writes no longer require public metadata resolution first.

For an episode, the request is shaped as:

```json
{
  "show": { "ids": { "imdb": "tt..." } },
  "episode": { "season": 2, "number": 5 },
  "progress": 34.92
}
```

A normal playback event therefore has the invariant:

```text
public metadata requests = 0
authenticated Trakt writes = 1
```

Canonical Trakt IDs may still be learned from the successful scrobble response for diagnostics/alias state, but that learning is no longer a prerequisite for the write.

### Stop semantics

Trakt and AIOStreams use different watched thresholds.

- Trakt `/scrobble/stop` completes around 80%.
- AIOStreams defaults to 90% for `played=true`.

rc.3 therefore uses a hybrid rule:

```text
AIO stop < 80%, played=false
  -> /scrobble/stop
  -> Trakt stores resumable progress

AIO stop 80-89%, played=false
  -> /scrobble/pause
  -> do not mark watched early

AIO played=true
  -> /scrobble/stop
```

This borrows Odin's direct stop path without copying the threshold mismatch.

### History dedupe without resolver dependency

v1.1 semantic history dedupe remains active.

When canonical Trakt IDs are not known before the write, rc.3 keys the short-lived semantic marker from stable AIOStreams item identity. This keeps repeated same-state `played` / `unplayed` echoes from creating another Bridge history mutation.

A successful completed stop also seeds the same dedupe state for:
- current Trakt `action=stop`;
- legacy `action=scrobble`;
- accepted 409 duplicate completion.

### Rate-limit recovery lanes

A headerless/unnamed 429 is no longer assumed to prove that both authenticated read and write lanes are blocked.

- POST/PUT/DELETE 429 -> cool write lane.
- GET 429 -> cool read lane.
- if both independently fail, both cool independently.
- explicit Trakt rate-bucket metadata still wins when provided.

This keeps a recovery pull possible after a failed write instead of pre-emptively disabling the read path.

## AIOStreams scheduler finding

The HomeDocker host currently runs AIOStreams 2.35.9 with no `WATCH_STATE_*` overrides.

A source and SQLite audit showed that AIOStreams' actual scheduler is controlled by its own runtime settings rather than the addon's manifest hint. The active Odin and AIOMetadata sinks were scheduled roughly 1800 seconds between background pulls.

This explains why a native Trakt write can be visible immediately in Trakt yet remain stale in AIOStreams until the next pull/on-demand refresh.

rc.3-A intentionally does **not** change AIOStreams scheduling. That variable is isolated for a later activity-aware pull canary.

## HomeDocker canary acceptance

Keep native Trakt enabled on VidHub and Strand.

Required checks:

1. health/readiness remain good; schema remains 1; zero unexpected restarts.
2. normal episode playback produces no public resolver request.
3. one playback transition produces at most one authenticated Trakt write.
4. no resolver 429 appears in the playback critical path.
5. newer failed playback still blocks older stale retries.
6. VidHub -> Strand partial resume succeeds repeatedly.
7. Strand -> VidHub is observed separately; intermittent stale pull is not misclassified as a transport failure.
8. repeated AIO `played` events do not create duplicate Bridge history rows.
9. explicit Mark Unplayed remains functional.
10. 80-89% unfinished stop remains resumable and is not marked watched.
