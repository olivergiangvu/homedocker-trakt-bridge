# v1.4 security boundary after R23D-2B1S Docker API bypass

**2026-10-16. Draft design evidence only; no authorized HomeDocker apply or v1.4 Stable release.**

## What is and is not a realistic trust boundary

A process with unrestricted access to the local Docker Engine API effectively has host-root-equivalent control. It can connect a fake gateway to any Docker bridge, start extra containers, alter privileged networking and bypass **a user-space admission script**. The B1S adversarial disposable runner proves a narrower specific instance: pausing the B1R systemd guardian, deleting the owned nft table, then issuing `docker network connect` and `docker start` directly can make an otherwise isolated fake TCP relay reachable. On resumption, the B1R guardian detects and disconnects, but **only after an exposure interval**. This is a deliberately demonstrated *privileged actor* threat, not evidence that a normal unprivileged browser or Jellyfin client bypasses network defenses.

**No amount of systemd unit ordering alone can promise resistance to a malicious root-equivalent Docker administrator on the same host.** For v1.4 release, either explicitly include trusted root/Engine admins in the threat model or require a truly independent enforcement domain (e.g. upstream physical firewall/device or hypervisor/VM boundary, where Docker root does not control enforcement). Do not label the current B1R monitor or B1P nft lease as a tamper-resistant control.

## Proposed practical boundary for existing HomeDocker

- **Trusted:** Linux root/authorized SSH administrators, Docker daemon/Engine API principals, Portainer/Dockhand operators **to the extent they have direct Engine access**. Never assume `docker.sock:ro` makes the Docker API read-only: the socket protocol can still permit writes.
- **Untrusted:** WAN users, arbitrary Jellyfin-compatible clients, third-party extensions/addons, media metadata and stream URLs, upstream provider responses. Grant them **no Docker API, no host networking privileges, no mutable history database credentials**.
- **Mediated:** AIOStreams-compatible Gateway may become reachable to explicitly opted-in authenticated clients only after exact identity/session test acceptance, through the existing host nginx controlled route; no new direct WAN-published Gateway port. The Trakt canonical watched/history writer remains singular. CrossWatch/Jellyfin/Remux state is secondary as previously agreed.
- **Isolation:** keep `JELLYFIN_GATEWAY_ENABLED=false` by default, use `--network none` / stopped until gated admission, pin reviewed images by digest, prohibit `--privileged`, `--network host`, broad writable host bind mounts, Docker socket mounts in new Gateway, and any broad port forwarding. Existing AIO/Remux/Portainer stacks are not altered for this design study.
- **Monitoring:** any nft/TC loss must fail closed or detach as tested in a disposable environment, but polling will not provide zero-time leakage. A bounded allowed-flow lease can be part of defense-in-depth only if its underlying kernel policy cannot be silently removed by an untrusted actor. State detection/stop latency and accepted residual windows explicitly.

## Acceptance consequences

1. Keep **`V140_STABLE_RELEASE_HOLD`** until application/auth identity checks, actual client resume/history tests and disaster recovery meet documented gates.
2. Treat B1S privileged Docker bypass as a confirmed security finding. If the required assurance is literally *resistant to compromised Linux root or any Docker socket client*, the **current single-host Docker architecture cannot satisfy it**; deploy in a separate VM/security domain with independently controlled upstream firewall, or change the requirement.
3. A QEMU guest boot-ID change plus systemd/Docker default network hold, even if independently verified, is **not proof** that production Gateway daemon and its tc/nft guards survive true cold boot. The full combination must be tested on a disposable rebooting VM before claiming production qualification.
4. Gather **read-only** HomeDocker socket and network inventory before any changes. Identify existing Engine API consumers (such as Portainer, Dockhand, WUD if actually mounted), who can manage them, guest route/host nginx, exact container restart policy, and Rollback RC6. Do not stop, disconnect, prune, or remount those unrelated services simply because they possess legitimate Engine access.
5. Release stages should be auditable: frozen scoped v1.4 candidate and digest, immutable backup including current Bridge DB/OneDrive metadata, read-only preflight, explicit opt-in testing on localhost/LAN, live idempotency/history integrity verification, observable rollback, then promotion to stable. No stage may be inferred solely from green GitHub tests.

**Current status:** All prior B1K–R labs are scoped development evidence; B1S privileged bypass remains an explicit NO-GO for any security claim that an authorized Docker API actor cannot bypass admission. v1.4.0 is neither published nor deployed on HomeDocker.
