# v1.2 native-Trakt coexistence hardening

Tracking issue: #58

## Production requirement

HomeDocker keeps native Trakt enabled on capable clients such as VidHub and Strand. The bridge must coexist with those writers rather than require them to be disabled.

Trakt's authenticated mutation budget is scoped to the user, so the bridge cannot reserve the account's write capacity for itself. v1.2 therefore focuses on being a good concurrent writer:

- serialize and pace its own writes;
- honor upstream cooldowns;
- never replay an older AIOStreams playback transition after a newer one;
- keep reads available when Trakt explicitly identifies a write-only limit;
- preserve enough sanitized upstream diagnostics to explain 422/429 responses.

## Confirmed v1.1 behavior

v1.1 already spaces bridge POST/PUT/DELETE calls by 1100 ms and persists a Retry-After cooldown.

Production evidence showed a different failure mode:

1. AIOStreams queued playback events while Trakt returned 429.
2. Newer playback advanced well beyond the queued state.
3. A newer pause was rejected with 422.
4. Old AIOStreams retries later succeeded and rewound Trakt resume state.

The fix must therefore use **event time**, not progress, as the ordering authority. Seeking backwards is valid; replaying an older event is not.

## Phase A — correctness and observability

### Playback watermark

For `start`, `pause`, and `stop`, resolve the event to the canonical Trakt movie/episode and persist the newest AIOStreams `at` timestamp seen for that item.

A retried transition is stale only when:

`incoming.at < newestSeen.at`

Equal timestamps are allowed because multiple legitimate transitions can occur inside the same AIOStreams one-second timestamp resolution.

The watermark is recorded **before** the upstream Trakt call. This matters when the newest event itself receives 429 or 422: an older retry must still be prevented from overtaking it.

The watermark does not compare progress, so a newer seek from 80% back to 30% remains valid.

### Error diagnostics

For non-success Trakt responses retain only safe, bounded fields:

- HTTP status;
- endpoint and method;
- Retry-After;
- parsed X-Ratelimit bucket metadata;
- a short upstream error/message/description string.

Never persist authorization headers, tokens, credentials, or arbitrary full response bodies.

## Phase B — bucket-aware cooldowns

Trakt documents separate authenticated GET and authenticated mutation limits.

- `AUTHED_API_POST_LIMIT` => write cooldown only.
- `AUTHED_API_GET_LIMIT` => read cooldown only.
- unknown/headerless 429 => shared/security cooldown, blocking both.

This preserves pull/read convergence during a confirmed write-only throttle while remaining conservative for security/abuse responses.

## Phase C — bounded pause recovery

Do not implement until Phase A captures the real 422 body in production.

If evidence confirms that `/scrobble/pause` fails because no active scrobble exists after a lost start, recover once with the existing write pacer:

`start(current progress) -> pause(current progress)`

Do not retry arbitrary 422 responses.

## Deferred write reduction

A recurring partial-playback sequence emits `stop/pause -> unplayed`. This may be a client compatibility echo. Observe it first; do not suppress explicit `unplayed` semantics without stronger evidence.

## Release discipline

- main/production stays v1.1.0 during development;
- development branch: `investigate/v1.2-native-trakt-hardening`;
- unit/integration tests must cover stale ordering, equal timestamps, backwards seek, restart persistence, write-only vs shared 429, and unchanged v1.1 history dedupe;
- publish a v1.2 RC only after CI passes;
- canary with native Trakt enabled on VidHub and Strand.
