## Upstream source findings (checked 2026-10-14)

AIOStreams \`main\` contains a join mechanism for \`match_key\` but it **does not automatically bridge two distinct raw IMDb IDs**:

| Source | Observed mechanism | Limitation |
| --- | --- | --- |
| \`packages/core/src/watch-state/types.ts\` | \`itemKeyFor\`, \`seriesKeyOf(baseId)\` create \`e|...\` and \`s|...\` keys | Different IMDb IDs create different series keys |
| \`packages/core/src/watch-state/canonical.ts\` | \`matchKeyFor\` derives match keys from anime IDs and mapping dataset for \`tmdb:\`/\`tvdb:\` | Raw IMDb A vs raw IMDb B not unified by generic mapping |
| \`packages/core/src/watch-state/lookup.ts\` | \`latestSpellings\` de-duplicates by \`matchKey ?? itemKey\` | Cannot join two histories with no shared verified \`matchKey\` |
| \`packages/server/src/routes/jellyfin/library.ts\` | Jellyfin \`/Shows/NextUp\` reads \`provider.recentSeries\` and deduplicates by \`String(next.SeriesId ?? next.Id)\` | Two distinct packed Jellyfin SeriesIds can produce two cards even if logically one Trakt show |
| \`packages/core/src/metadata/id-mappings.ts\` | Source dataset maps IMDb↔TMDB/TVDB and **drops provider groups claimed by multiple IMDb IDs** | Cannot assume the dataset proves equivalence of two different IMDb IDs |

### Known verified fixture

Trakt show 263102, canonical IMDb \`tt44051354\`; AIO local alias \`tt44094505\`; TMDB 276470. Two independent series timelines, no shared \`match_key\` in the original RC7 investigation. Trakt's correct S01E10 resume plus stale local alias S01E09 produced two NextUp cards. RC7 one-time official AIO Jellyfin dropped preference masked duplicate in 50-item capture without removing 18 historical rows. A future play under old alias can undo that preference; it **is not** durable normalization.

## Phase 1: Bridge verified identity graph (implemented in feature branch)

\`src/identity-continuity.mjs\` stores verified canonical/alias relationships under \`identity-graph:v1:{profileId}\` in Bridge's **own** \`media_cache\`. It records mappings only after an **authenticated successful Trakt scrobble** returns canonical \`show.ids.trakt\` and \`show.ids.imdb\`, and the source event has an IMDb media ID. Recorded rows are keyed by Trakt show ID; they preserve *multiple* verified raw AIO IMDb aliases rather than overwriting one preferred value.

Safety invariants:
- No new public Trakt lookup, no Trakt history/replay write, no AIO source/schema or SQLite access;
- Profile scope, strict ID validation and bounded graph/candidate sizes;
- Reject canonical/trakt ID disagreement, TMDB/TVDB drift and cross-show alias claims to conflict quarantine;
- Never infer identity from title/year/episode numbering, or from a lone unverified IMDb query;
- \`verifiedCanonicalForImdb\` returns null for unresolved or quarantined IDs;
- \`identityEquivalenceProposal\` emits only conflict-free verified relationships with a clear \`NOT_SUPPORTED_BY_AIO_UPSTREAM_YET\` marker;
- No change to \`PULL_IDENTITY_MODE=trakt\`, native-Trakt precedence, source-scope identity or current \`AIO_RECONCILER_MODE=compare\` behavior.

**This code does not claim to rewrite AIO NextUp.** It prepares a proof-driven producer for the required upstream interoperability contract.

## Read-only verification against the running HomeDocker AIO latest

The **actual installed AIO image may lag or lead the public upstream main branch**. The operator can run `scripts/audit-aio-identity-readiness.py` with `sudo` *without exposing secret env vars*:

```bash
sudo python3 ~/audit-aio-identity-readiness.py
```

This prints only AIO image ID prefix, `ID_MAPPINGS_ENABLED`/`WATCH_STATE_PULL_ENABLED`/`WATCH_STATE_REPORT_ENABLED` booleans (defaults marked as upstream-source assumptions), and **per-series aggregate** number of episode rows, NULL `match_key` rows and active resume rows under the exact known AIO sink/user/persona. It does not print UUIDs, persona, image env credentials, event bodies or watched titles; it issues no HTTP calls, database writes or Docker mutation.

This audit cannot prove cross-IMDb identity equivalence by itself: **both sides having populated match keys is not proof that they resolve to the same exact match key**. A follow-up view of distinct, redacted match-key intersections must only be built once we know actual schema and the correct scope. Do not use a broad full-DB scan or public dump of every watch-state row.

### Phase 2 prototype (never deployed)

`experiments/aio-nextup-identity-projection.mjs` and its Node tests implement an **in-memory read-only projection** over mock AIO `watch_state` rows. With explicitly verified show ID 263102 linking canonical `tt44051354` to raw `tt44094505`, the 10+8 timeline is displayed as **one logical-series group without altering any episode row**. Subsequent playback under the obsolete IMDb alias becomes one same canonical display group, while separate users/personas and distinct/unverified shows stay separate.

A simultaneous incompatible pair of active resumes is reported `AMBIGUOUS_RESUMES_REVIEW` rather than silently discarded. This prototype intentionally does **not** resolve metadata, stream Jellyfin endpoints, modify AIO `recentSeries`/NextUp, write match keys to AIO, or guarantee real-client behavior. Upstream adoption and live qualification remain release blockers.

## Phase 2: Proposed OPTIONAL Watch State equivalence extension in AIO

**Not yet supported by AIO; must be implemented upstream and tested with AIO \`latest\` before enabling Bridge emission.** Do not add unknown JSON fields to a production manifest as a workaround.

Suggested payload extension in a tracker-owned \`watch_state.pull\` response:

\`\`\`json
{
  "identityEquivalences": [
    {
      "kind": "series",
      "canonical": { "trakt": 263102, "imdb": "tt44051354", "tmdb": 276470 },
      "verifiedAliases": ["tt44094505"],
      "proof": "successful_trakt_scrobble_response"
    }
  ]
}
\`\`\`

Upstream acceptance implementation sketch:

1. Validate the **exact authenticated tracker sink/user/persona**, \`kind=series\`, valid canonical Trakt ID and IMDb IDs; do not share mappings across users.
2. Treat a verified canonical relation as an **equivalence component for matching**, not as a destructive rewriting of \`item_key\` or \`series_key\`. Preserve all historical watch rows, timestamps, play counts and the original source spelling.
3. For both aliases, give \`matchKeyFor\`/reconciler access to the same logical-series group (or a source-maintained \`canonical_group_key\`). Import paths must safely reconcile both spellings, and all local playback events must still retain their original source identity.
4. **NextUp and Resume** must group on *verified logical series*, not just raw packed Jellyfin \`SeriesId\`. The position winner must be decided from exact per-episode resume/played timestamps and declared canonical precedence, not title or last array element. If conflicting simultaneously active resumes remain incomparable, emit a diagnostic conflict and avoid destructive repair.
5. A new playback event on formerly dropped alias must retain the equivalence, regardless of \`dropped\` preference state. No repeated automatic drop needed.
6. The scope of provider mappings and canonical migration must be strictly opt-in for tracker integrations that actually supply verified evidence; upstream default continues to handle existing addons without change.
7. Version/capability negotiate via AIO Watch State v2 + optional flag before Bridge emits the new field; unrecognized fields must never alter current behavior.

**Do not submit an unsolicited AIO upstream PR describing a private home-server ID/metadata incident or credentials.** First qualify with a neutral synthetic fixture, then propose the minimal additive contract to upstream maintainers. Production AIO continues \`ghcr.io/viren070/aiostreams:latest\`; never fork/pin its running image to deliver this feature.

## Acceptance tests before declaring permanent normalization

- Original two-IMDb fixture: one Jellyfin NextUp card before and **after** playing on the obsolete alias; no destructive drop required.
- Switch playback clients with different provider spellings and across Bridge/AIO restarts; one correct newest resume and no overwritten watched timeline.
- AIO \`latest\` update, then contract smoke of all NextUp pages (not just first 50), Resume and active Jellyfin clients.
- Native Trakt new-mark and rewatch, manual watched/unwatched, episode ordering, season and anime absolute numbering; no false Trakt history rewrites.
- Cross-show conflicting IMDb assignment and ambiguous Trakt/TMDB mismatch: no silent join, no preference overwrite, no history deletion; explicit quarantine.
- No increase in Trakt 429s, no speculative poll amplification, no extra uncontrolled GET/POST traffic.
- Rollback Bridge pinned image and restore DB backup on fresh hardware must preserve canonical graph or harmlessly fall back to non-normalized behavior.
- Production RC6/Stable deploy **must remain paused** if the owner requires this guarantee as a release blocker.
