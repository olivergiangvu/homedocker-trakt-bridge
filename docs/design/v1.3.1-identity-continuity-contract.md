# v1.3.1 Identity Continuity — HOME-OWNED BRIDGE / GATEWAY ONLY

**Status:** implementation and CI experiments inside HomeDocker Trakt Bridge, not released/deployed. **Hard constraint reaffirmed 2026-10-14 by operator:** NEVER edit, patch, fork, submit changes to, or pin AIOStreams source/image. AIOStreams stays `ghcr.io/viren070/aiostreams:latest` and upgrades independently. Its officially exposed configuration, metadata/provider ordering and public Jellyfin API may be used. No AIO SQLite writes. No automatic repeated `Drop show`.

## Baseline and confirmed RC7 fixture

The live read-only AIO SQLite audit (2026-10-14) observed image `sha256:5e1e1fcccdfd...`; current Bridge sink owner held **10 canonical rows** under `s|tt44051354` (10 NULL match_key, 1 resume) and **8 alias rows** under `s|tt44094505` (8 NULL match_key, 0 resume). The one-time RC7 official Jellyfin `dropped` preference hides the older timeline, preserving all 18 episode rows. It is not identity convergence and can be undone by further playback on the alias.

AIO upstream does not automatically join different raw IMDb `series_key` rows: its `WatchStateRepository.recentSeries` groups by `series_key` and optional mapped match keys; its Jellyfin `/Shows/NextUp` de-duplicates returned items by packed `SeriesId`. This is relevant **source behavior to accommodate** in our adapter, NOT a reason to modify upstream.

AIO Jellyfin episode items expose opaque `SeriesId`; episode-level `ProviderIds` may be per-episode, not show ID. AIO's own series item DTO populates `ProviderIds` from the show's metadata. The Bridge-owned adapter must resolve a SeriesId to show IMDb via AIO's **existing authenticated series detail endpoint**, using the identical user authorization/scope. Never parse opaque IDs or infer equivalence from the episode title or episode ProviderIds.

## Architecture — two permitted, complementary remedies

1. **Prevent future split where official external settings suffice.** Audit AIO provider priority, metadata mappings and active user-config settings using supported interfaces. Apply only documented external settings, after an explicit config backup and before/after audit. Do not assume `ID_MAPPINGS_ENABLED` unset means mappings are effective: the previous audit reported default *source* assumptions, not a verified loaded dataset.
2. **HomeDocker-owned compatibility gateway for Jellyfin API clients.** A small Bridge-side adapter / sidecar is the only code-modified component. It forwards all unrecognized Jellyfin paths unchanged to the existing AIO endpoint, and MAY apply a **read-only response projection** specifically to `GET /Shows/NextUp` and later `GET /UserItems/Resume` once paging/user-scope requirements are separately qualified. Add the gateway via native host nginx routing or explicit client base URL change; do not modify the AIO container or bind its existing port. Direct AIO clients bypassing our gateway necessarily retain upstream behavior.

**Bridge canonical registry** (`src/identity-continuity.mjs`) stores verified Trakt show IDs with multiple IMDb spellings under the existing Bridge SQLite media_cache, profile-scoped. It learns only from a successful authenticated Trakt scrobble show response, rejects explicit provider-ID disagreement and quarantines collisions; no title/year guesses, speculative Trakt reads or extra history writes. Data is a source for our gateway, **not** for an unsupported AIO pull extension.

**Implemented in draft Bridge source, not deployed:** `src/jellyfin-gateway.mjs` runs a **separate opt-in NextUp-only HTTP listener** inside the HomeDocker Bridge process, disabled by default. It requires the exact AIO Jellyfin user ID and connected Trakt profile ID in the Bridge's own environment. It forwards the original Jellyfin token to AIO's existing `GET /Users/Me`, then to `GET /Items/{opaqueSeriesId}` for each bounded series metadata lookup, and calls `src/jellyfin-nextup-filter.mjs` only when the identity graph proves the alias relationship. The response preserves original episode IDs and watched/resume state; errors and competing resumes pass through as received. Other Jellyfin paths are **NOT proxied by this listener**: nginx must continue sending them to the existing AIO `latest` route. Synthetic Node HTTP regression tests pass. This is an implemented endpoint and filter, **not yet a live nginx or client deployment**, and it does not merge AIO watch-state rows.

## Required gateway controls before canary

- **Opt-in OFF by default.** First prove NextUp requests from Remux, Trellis, Strand and all relevant Apple Jellyfin API clients actually route through the chosen stable nginx hostname. Clients reaching AIO directly cannot benefit from our response projection.
- Reverse proxy must preserve the complete upstream status, required Jellyfin headers/auth, URL path/query, response types and streaming/WebSockets. Never log tokens or Jellyfin credentials. Do not cache/show another user's NextUp, and never use raw title/episode similarity to normalize.
- Limit metadata lookups (up to the bounded 50-card current AIO NextUp page), reuse existing authenticated AIO series details, add small user-scoped TTL cache without storing credentials, and pass through the original reply on error/unknown IDs.
- View item selection is **non-destructive**: no fabricated new Jellyfin ID, no direct watch-state writes, no Trakt/SQLite writes. A remaining two-resume ambiguity must be visible/diagnosable, not silently overwrite or delete a resume.
- AIO upstream version remains `latest`; upgrade independent; no fork, patch or upstream PR. Bridge/sidecar can pin its own immutable digest for controlled canary and rollback.
- Keep current native Trakt write priority, true rewatches, mark played/unplayed and watched history. Never replace AIO's user-specific playback/watch-state with a different account's data.

## Acceptance and exclusions

Complete release requires actual client-facing Jellyfin NextUp **and Resume** observations through our gateway, including: original 10+8 rows, new playback using former alias, AIO latest update, a restarted Bridge, restored backup, and different user/persona/client. Confirm one correct card when there is sufficiently verified, non-conflicting playback evidence, with full history preserved. In ambiguous cases return original cards with an explicit diagnostic: safety wins over cosmetic forced dedupe.

**Implemented in draft only:** scoped HTTP NextUp listener, same-token `/Users/Me` verification, same-token existing Jellyfin series details, bounded fail-open response filter and synthetic tests. **Not implemented/deployed:** host nginx/Compose opt-in canary, client path coverage, Resume pagination handling, multi-user mappings, and live client regression. Green synthetic HTTP tests are not production acceptance. See [canary operations guide](../ops/JELLYFIN-NEXTUP-GATEWAY-CANARY.md). v1.3.1 is **not released**, Issue #93 stays open and PR #94 remains draft. Published v1.3.0 tag and running RC6 image are unchanged.

## HomeDocker canary isolation decision after verified RC6 audit

The operator's latest read-only readiness audit explicitly reports `legacy_alias_timestamp_valid=true`, `legacy_cache_unexpired=true`, `legacy_owner_connected=true`, `legacy_canonical_matches=true`, `legacy_alias_matches=true`, and `aio_has_network_dns_alias=true`. `verified_graph_present=false` is expected because no importer has run.

**Prefer a standalone gateway-only canary, not a second full Trakt Bridge, and do not connect production RC6 to `media_core_net`.** The verified single RC6 pair is exported by `scripts/export-canary-identity-proof.py` using a production SQLite `mode=ro` query into a new private, token-free `identity-proof.json`. The dedicated `Dockerfile.gateway-canary` runs `src/gateway-canary-entry.mjs`, which loads this one sanitized proof via `src/gateway-standalone.mjs` into a read-only in-memory graph and starts **only** `src/jellyfin-gateway.mjs`. It imports **no Bridge DB/Trakt client/reconciler**, mounts no production SQLite and needs no OAuth credentials. It can join the existing media network independently, expose only a host-loopback NextUp listener, and be removed without any change to RC6 or AIO.

The general-purpose `JELLYFIN_GATEWAY_LEGACY_IMPORT=off|preview|apply` implementation remains regression-tested for eventual Bridge upgrades, but is **not** the preferred means of seeding this isolated RC7 fixture canary. Do not run it against the live RC6 DB. CI now builds and smoke-tests the isolated gateway image read-only without privileged capabilities.

**Not yet qualified:** real AIO authenticated series ID lookup, client-route proof, full NextUp 10+8 behavior after alias playback, Resume pagination, and all-client normalization. The exported sanitized graph alone is not a production fix. See [canary operations guide](../ops/JELLYFIN-NEXTUP-GATEWAY-CANARY.md).

## RC7 C10/C10.1 — Resume API pagination contract (2026-10-15)

Live authenticated HomeDocker AIO exposes both `GET /UserItems/Resume` and `GET /Users/{userId}/Items/Resume`. For `Limit=20` modern/legacy ordered ID/position signatures matched on StartIndex 0 and 20, with no cross-page duplicates and stable first-page recheck. 40 returned entries included 31 episodes and 9 movies; all had nonzero resume positions. AIO returned `TotalRecordCount=20` at StartIndex 0 and `TotalRecordCount=40` at StartIndex 20. Upstream source constructs at most StartIndex+Limit watch rows and uses the number of materialized items as total; **this is a fetched-prefix count, not a guaranteed library-global total**.

Safety decision: Phase-0 Resume support in draft is **explicitly opt-in raw upstream passthrough only**. It preserves the existing movies, episodes, ticks, original metadata, item order, status, query parameters and totals. No Resume deduplication is authorized while all cards are active and the upstream total/paging boundary is not globally proven. A future normalization pass requires proven snapshot completeness and cross-page context; otherwise fail-open. Standalone canary env `JELLYFIN_GATEWAY_RESUME_PASSTHROUGH=true` controls this opt-in, disabled by default. No production nginx/client routing, AIO, Bridge RC6 or DB changes.
