# G2-1B — Odin NextUp excluded-query key taxonomy (diagnostic only)

## Confirmed real HomeDocker result

On 2026-10-18, the operator ran a real macOS Odin NextUp/Resume shadow pilot at SHA fdd2a5d77e949022df611af5df45b5fcc6b3429b. Real Odin produced one NextUp and one Resume request. AIO client pass-through returned four HTTP 2xx responses and zero 4xx/5xx. Actual v1.4 Gateway completed 1/1 shadow GET, 2xx, 1871ms total, upstream NextUp 2xx in 1811ms. No timeout, transport failure, playback/history write, production SQLite write, or filtered client response.

In that session, gateway_identity_excluded_query=1; gateway_identity_eligible=0; 0 User/Me, 0 metadata GET, 0 alias removals. This **proves** the exact Odin NextUp request contained at least one of SeriesId, ParentId, or StartIndex parameters, and the Gateway correctly preserved AIO response. The captured aggregate cannot distinguish which key, whether offset was zero or which media the client requested. It does not prove the identity graph/algorithm is wrong.

## Added exact-key shape counters

The code retains the exact **existing** conservative exclusion rule. When a NextUp GET has one of the protected query keys, and only then, it increments exactly one of:

- gateway_excluded_series_id_only
- gateway_excluded_parent_id_only
- gateway_excluded_start_index_zero_only
- gateway_excluded_start_index_other_only (nonzero, malformed, or duplicate values)
- gateway_excluded_multiple_keys (at least two distinct protected keys)

StartIndex zero is only detected when it is the exact single string value 0. The HTTP response is NEVER filtered based on this diagnostic. Only integer aggregate counts are returned; neither query values, media IDs, credentials, user IDs, playback positions nor URL paths are logged or saved. This categorization is not a capture of the exact query string.

New synthetic HTTP end-to-end cases exercise ParentId, StartIndex zero/nonzero/malformed/duplicate and mixed protected keys. All preserve the exact source response, do no user/metadata lookup, and leave both production write counters at zero. The existing same-user alias 2-to-1 synthetic case still qualifies, but the live Odin client has not done so.

## What the result will mean for the architecture

1. If **StartIndex zero only**, evaluate a distinct Draft proposal for a *first-page-safe* filter. Do not simply remove the existing gate; AIO's TotalRecordCount and paging can differ from actual library totals and must remain intact. Even this condition does not guarantee two valid Items.
2. If **StartIndex other** or **multiple keys**, filtered NextUp could violate offset/pagination semantics. Keep pass-through until user/response/pagination invariants are explicitly tested.
3. If **SeriesId** or **ParentId**, the client requested a scoped NextUp response. Automatically removing an alias episode based on the global graph could break a specific series/parent view; first determine product semantics, not media identity values.
4. If any request with **no protected keys** is later observed, the existing identity eligibility counters govern, including same-user validation before metadata queries and fail-open on ambiguity.

No more preflight repeats are needed: RC6 digest, Node24, loopback and actual Odin shadow traffic already passed. One **optional** short repeat of the existing separate pilot under a new immutable SHA would expose the key taxonomy. It should only be chosen if the query-shape result will change the next design decision. No attempt to induce playback or mark watched is needed.
