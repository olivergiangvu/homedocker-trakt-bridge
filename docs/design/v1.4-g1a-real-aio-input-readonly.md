# G1A — Real AIO identity and NextUp *input* evidence (read-only)

**G1 remains OPEN.** This is the first practical, safe operator checkpoint after [G0 PR #119](https://github.com/olivergiangvu/homedocker-trakt-bridge/pull/119); it does not import the graph, start an identity Gateway, route client traffic or change any HomeDocker service.

## What this verifies

`scripts/audit-v140-g1-live-inputs.py` on the HomeDocker host:
- Finds the exact **running** production `trakt-bridge` Docker `/app/data` mount and reads only the existing legacy alias/graph cache and connected profile flag using SQLite URI `mode=ro`, `PRAGMA query_only=ON`. Fails closed on changed scope, expiry, cross-show conflict or unexpected graph. No tokens read from SQLite and no DB writes.
- GET public AIO Jellyfin `http://127.0.0.1:3240/jellyfin/System/Info/Public` using local loopback, no proxy/redirect.
- With **separate explicit operator confirmation**, asks for an existing token via hidden interactive prompt (all HTTP **GET**), OR asks for configuration username/password via hidden prompt, sends **one AIO login POST** (may create an AIO session), then performs GET-only `/Users/Me`, `/Shows/NextUp?Limit=20`, and bounded authenticated `/Items/{SeriesId}` metadata reads. A second NextUp GET validates source stability.
- Maps metadata **within local Python process memory only** to the verified legacy canonical/alias candidates; prints only numeric totals and status codes. Does NOT emit raw login response, token, user/profile/media/IMDb ID, watch position or item details, and does not store any credentials.
- Classifies positive alias-pair presence versus no pair or ambiguous competing active resumes. Does **not** filter live output, prove that an installed Gateway uses the same account, assert one user ↔ one Bridge profile mapping, prove real client NextUp traversal or imply a production release.

### Execute read-only preflight first

On SSH HomeDocker, clone the **pinned G1A PR commit** (check PR head/CI) and run:

```bash
sudo python3 -B scripts/audit-v140-g1-live-inputs.py --mode preflight
```

Expected `PREFLIGHT_READY_NO_AUTH`, connected legacy profile count one and zero AIO authentication/watch-state requests. This may STOP if real bridge data changed since R19/R20; do not force it.

### Choose ONE opt-in authentication mode (only after preflight PASS)

**Existing AIO/Jellyfin token (recommended, no session creation):**

```bash
sudo python3 -B scripts/audit-v140-g1-live-inputs.py \
  --mode existing-token --confirm V140_G1_AIO_EXISTING_TOKEN_GET_ONLY
```

Token is entered only at the hidden SSH prompt. This requests GET only.

**AIO login when no token is available** (one POST login, creates AIO session, then GET only):

```bash
sudo python3 -B scripts/audit-v140-g1-live-inputs.py \
  --mode login --confirm V140_G1_ONE_AIO_LOGIN_READONLY_NEXTUP
```

Login alias/config UUID and password/PIN are entered at two hidden SSH prompts. Do not paste token/credentials, raw HTTP responses or `docker inspect` into chat.

Results may say:
- `LIVE_PAIR_PRESENT_NEEDS_CANDIDATE_GATEWAY`: one or more *source* canonical/verified aliases coexist, **not yet filtered by Gateway**.
- `NO_LIVE_PAIR_IN_SAMPLE_SYNTHETIC_POSITIVE_STILL_REQUIRED`: live NextUp sample has no candidate, **NOT a failure of Gateway logic**; separate G0 synthetic positive 2→1 is already proven.
- `SOURCE_CHANGED_INCONCLUSIVE`: NextUp changed during sampling, retry only after reviewing the safe reason.
- `G1A_STOP_*`: preconditions invalid, authentication/metadata not usable or original Bridge identity changed. STOP and review before retry.

All results print `profile_identity_binding_verified=false`, `active_candidate_identity_graph_verified=false`, `g1_complete=false`. These are intentionally **truthful** until G1B isolated candidate integration verifies exact AIO user/profile graph mapping and Gateway actual response.

### Non-negotiable

No production DB migration, `docker run`, `nginx` edit, live Gateway rollout, AIO change, Trakt call, cleanup, or additional history writer in G1A. The operator must explicitly choose token-only versus login (a POST that may create an AIO session). Release HOLD remains.
